# Архитектура

Flux Planner — Telegram Mini App на SvelteKit. Принцип: **local-first**. Приложение
открывается и работает без сети, а сервер догоняет в фоне.

## Поток данных

```
Telegram → initData → проверка подписи на сервере
                              ↓
                      авторизованный пользователь
                              ↓
   plannerStore (руны) ←→ IndexedDB ←→ очередь синхронизации ←→ API ←→ SQLite
                              ↓
                    производные значения → интерфейс
```

Ключевое: база **никогда не блокирует первую отрисовку**. Порядок такой:

1. Стор стартует на безопасных значениях по умолчанию, интерфейс рисуется сразу.
2. Гидратация из IndexedDB догоняет и перерисовывает.
3. Синхронизация с сервером идёт фоном и перерисовывает ещё раз.

## Слои

| Слой           | Где                                     | Задача                                                 |
| -------------- | --------------------------------------- | ------------------------------------------------------ |
| Типы           | `src/lib/types/`                        | Формы данных, общие для клиента и сервера              |
| Чистые расчёты | `src/lib/utils/`                        | Формулы без состояния: прогресс, стрики, финансы, даты |
| Состояние      | `src/lib/stores/plannerStore.svelte.ts` | Единственный источник истины                           |
| Сервисы        | `src/lib/services/`                     | Валидация и операции над состоянием                    |
| Хранилище      | `src/lib/db/`                           | IndexedDB, очередь синхронизации                       |
| Сервер         | `src/lib/server/`                       | Авторизация, база, ИИ, Telegram, уведомления           |
| Экраны         | `src/routes/`                           | Дашборд, аналитика, календарь, настройки, привычки     |
| Маршруты       | `src/routes/api/`                       | HTTP-эндпоинты                                         |

## Правила, на которых всё держится

**Один источник истины.** Производные значения (остаток калорий, прогресс, стрики,
итоги трат) нигде не хранятся — они вычисляются из записей. Хранить их отдельно
значит однажды показать пользователю два разных ответа на один вопрос.

**Деление в одном месте.** Все проценты считает `progressRatio` из
`utils/progress.ts`. Нулевая цель даёт 0, а не бесконечность: NaN в атрибуте SVG
ломает отрисовку молча.

**Запись сквозная, без общего `$effect`.** Каждый мутирующий метод стора сам
сохраняет затронутую запись. Общий эффект, следящий за всем состоянием, замкнул бы
петлю `state → save → load → state` и на гидратации перезаписал бы только что
прочитанное.

**Мягкое удаление.** Записи не стираются, а получают `deletedAt`. Без надгробий
удаление на одном устройстве неотличимо от «этой записи тут ещё нет», и второе
устройство вернуло бы её обратно.

**Отметки привычек не удаляются в полночь.** Меняется текущая дата, а чекбокс
определяется парой «привычка + день». История остаётся навсегда.
