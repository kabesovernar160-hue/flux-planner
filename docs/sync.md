# Синхронизация

## Принцип

Local-first. Изменение сначала попадает в IndexedDB и сразу видно в интерфейсе,
и только потом уезжает на сервер. Сеть может отсутствовать сколько угодно —
приложение полностью работоспособно.

## Протокол

### `POST /api/sync/push`

```json
{
  "changes": {
    "food": [ { "id": "...", "createdAt": "...", "updatedAt": "...", "deletedAt": null, ... } ],
    "habits": [], "completions": [], "finance": [],
    "nutritionDays": [], "financeDays": []
  },
  "settings": { "calorieGoal": 2100 },
  "settingsUpdatedAt": "2026-01-15T10:00:00.000Z"
}
```

Ответ: `{ "applied": { "food": 3 }, "serverTime": "..." }`

### `GET /api/sync/pull?since=<ISO>`

Без `since` отдаёт всё. Ответ: `{ "changes": {...}, "serverTime": "...", "settings": {...} }`.

Клиент сохраняет `serverTime` и присылает его как `since` в следующий раз.

## Очередь на клиенте

`src/lib/db/syncQueue.svelte.ts`

Отдельного журнала изменений **нет намеренно**. Каждая запись несёт `updatedAt`,
поэтому «что ещё не отправлено» вычисляется как «всё, что новее водяного знака».
Журнал пришлось бы держать в согласии с данными, и потеря одной его записи
означала бы потерю изменения навсегда.

Водяные знаки лежат в `localStorage`: `pulledAt` (отметка сервера) и `pushedAt`
(момент последней отправки).

Статусы: `idle`, `syncing`, `offline`, `error`.

Порядок внутри одного цикла: **сначала push, потом pull**. Так изменение, сделанное
только что, не будет затёрто более старой серверной версией той же записи.

## Разрешение конфликтов

**Last Write Wins по `updatedAt`.** Реализовано на уровне SQL:

```sql
ON CONFLICT (id) DO UPDATE SET ... WHERE excluded.updated_at > updated_at
```

Отставший клиент не откатывает свежие правки: его запись просто не применяется.
Все отметки времени — UTC ISO 8601, поэтому лексикографическое сравнение строк
эквивалентно сравнению моментов.

`id` и `createdAt` при слиянии не переписываются: первый — ключ конфликта,
второй фиксирует момент создания.

## Удаление

Надгробия. Удалённая запись получает `deletedAt` и продолжает синхронизироваться.
Клиент отфильтровывает такие записи при загрузке состояния — в одном месте,
в `sanitizeArray`, чтобы не забыть про это в каждом производном значении.

Полная очистка надгробий (compaction) пока не реализована — см. TODO ниже.

## Повторные попытки

Конечные: `2с → 8с → 30с → 120с`, дальше очередь ждёт следующего изменения или
явного `syncNow()`. Бесконечный ретрай при лежащем сервере съедает батарею
и трафик, а пользователю не помогает.

## Ограничения

- До 2000 записей в коллекции за один пакет.
- 60 запросов в минуту на адрес для каждого из эндпоинтов.

## Что не сделано

- **Compaction надгробий.** Они копятся вечно. Нужна фоновая чистка записей,
  удалённых больше N дней назад, на сервере и на клиенте.
- **Слияние настроек.** Сейчас документ настроек заменяется целиком по времени.
  Правка разных настроек на двух устройствах приведёт к потере одной из них.
- **Уведомление о конфликте.** LWW работает молча. Для заметок и сумм это
  приемлемо, но пользователь не узнает, что его правка проиграла.
