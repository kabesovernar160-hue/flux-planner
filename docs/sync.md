# Синхронизация

## Принцип

Local-first. Изменение сначала попадает в IndexedDB и сразу видно в интерфейсе,
и только потом уезжает на сервер. Сеть может отсутствовать сколько угодно —
приложение полностью работоспособно.

## Протокол

### `POST /api/sync/push`

```json
{
  "changes": {
    "food": [ { "id": "...", "createdAt": "...", "updatedAt": "...", "deletedAt": null, ... } ],
    "habits": [], "completions": [], "finance": [], "plan": [], "weight": [],
    "nutritionDays": [], "financeDays": []
  },
  "settings": { "calorieGoal": 2100 },
  "settingsUpdatedAt": "2026-01-15T10:00:00.000Z"
}
```

Ответ: `{ "applied": { "food": 3 }, "serverTime": "..." }`

`settingsUpdatedAt` — отметка самих настроек, а не записи пользователя.
Сервер применяет присланные настройки, только если она строго свежее
сохранённой; пока сюда уезжало время записи пользователя, оно не двигалось
при правке целей, и все изменения после первой отправки отвергались молча.

### `GET /api/sync/pull?since=<ISO>`

Без `since` отдаёт всё. Ответ:
`{ "changes": {...}, "serverTime": "...", "settings": {...}, "settingsUpdatedAt": "..." }`.

Клиент сохраняет `serverTime` и присылает его как `since` в следующий раз.
Настройки он принимает целиком, когда `settingsUpdatedAt` свежее локальной
отметки: построчного слияния у документа нет, побеждает более свежая версия.

## Очередь на клиенте

`src/lib/db/syncQueue.svelte.ts`

Отдельного журнала изменений **нет намеренно**. Каждая запись несёт `updatedAt`,
поэтому «что ещё не отправлено» вычисляется как «всё, что новее водяного знака».
Журнал пришлось бы держать в согласии с данными, и потеря одной его записи
означала бы потерю изменения навсегда.

Водяные знаки лежат в `localStorage`: `pulledAt` (отметка сервера) и `pushedAt`
(момент последней отправки).

Статусы: `idle`, `syncing`, `offline`, `error`.

Порядок внутри одного цикла: **сначала push, потом pull**. Так изменение, сделанное
только что, не будет затёрто более старой серверной версией той же записи.

## Коллекции

`food`, `habits`, `completions`, `finance`, `plan`, `weight` — таблицы записей,
каждая лежит в своём хранилище IndexedDB.

`nutritionDays` и `financeDays` — цели и бюджет дня. В интерфейсе это часть
документа под ключом-датой, а не список записей, поэтому перевод «документ ↔
строки протокола» собран в `localDb`: очередь синхронизации не должна знать,
как устроено локальное хранилище. Записям дня приписаны служебные поля
(`id`, `createdAt`, `updatedAt`); документам, сохранённым до их появления,
поля достраиваются при первом чтении и сразу записываются обратно — иначе один
и тот же день уезжал бы на сервер под новым идентификатором после каждого
запуска.

Коллекция, которой клиент ещё не знает, пропускается молча: новое поле
в протоколе не должно ронять синхронизацию целиком.

## Пустое устройство

Хранилище webview Telegram может исчезнуть в любой момент: клиент чистит его
сам, и человек этого не выбирал. Пустая база на устройстве поэтому значит
«мы не помним», а не «человек здесь впервые», и вся эта ветка построена
вокруг одного правила: **устройство без данных ничего не решает за сервер.**

- Нетронутые настройки помечены началом эпохи (`SETTINGS_NEVER_SAVED`)
  и не отправляются вовсе. Пока там стояло время создания документа, значения
  по умолчанию выглядели на сервере как самая свежая правка и затирали анкету
  и цели: человек заходил в бота и снова видел приветствие.
- `onboardedAt` и `profile` на сервере не стираются пакетом, в котором их нет
  (`mergePlannerSettings`). Пройденный первый запуск — событие, а не мнение;
  отменить его в приложении нечем, поэтому пакет без него означает «устройство
  ещё не знает». Это же прикрывает старые клиенты, которые ещё не обновились.
- Водяной знак не в счёт, если документа на устройстве нет. Знак лежит
  в `localStorage` и переживает чистку IndexedDB по отдельности, а с ним сервер
  отдал бы «изменения с тех пор», то есть ничего. Первый обмен в таком случае
  всегда полный.
- Настройки приезжают уже с входом: `POST /api/auth/telegram` возвращает
  `state: { settings, settingsUpdatedAt }`. Ждать первой синхронизации нельзя —
  до неё приложение видит пустые настройки и встречает знакомого человека
  анкетой для новичка. Приветствие поэтому показывается только после ответа
  сервера (`session.profileKnown`).

## Разрешение конфликтов

**Last Write Wins по `updatedAt`.** Реализовано на уровне SQL:

```sql
ON CONFLICT (id) DO UPDATE SET ... WHERE excluded.updated_at > updated_at
```

Отставший клиент не откатывает свежие правки: его запись просто не применяется.
Все отметки времени — UTC ISO 8601, поэтому лексикографическое сравнение строк
эквивалентно сравнению моментов.

### Записи, которых на день ровно одна

`weight`, `nutritionDays` и `financeDays` сливаются не по `id`, а по паре
«пользователь + день»:

```sql
ON CONFLICT (user_id, date) DO UPDATE SET ... WHERE excluded.updated_at > updated_at
```

Два устройства, создавшие запись одного дня офлайн, приходят с разными
случайными идентификаторами. Слияние по `id` упёрлось бы в уникальный индекс
`(user_id, date)` и уронило бы весь пакет вместо того, чтобы соединить две
правки. Идентификатор при этом остаётся за первой записью, а клиент принимает
серверный: локальная копия с другим `id` убирается при приёме.

`id` и `createdAt` при слиянии не переписываются: первый — ключ конфликта,
второй фиксирует момент создания.

## Удаление

Надгробия. Удалённая запись получает `deletedAt` и продолжает синхронизироваться.
Клиент отфильтровывает такие записи при загрузке состояния — в одном месте,
в `sanitizeArray`, чтобы не забыть про это в каждом производном значении.

Полная очистка надгробий (compaction) пока не реализована — см. TODO ниже.

## Повторные попытки

Конечные: `2с → 8с → 30с → 120с`, дальше очередь ждёт следующего изменения или
явного `syncNow()`. Бесконечный ретрай при лежащем сервере съедает батарею
и трафик, а пользователю не помогает.

## Ограничения

- До 2000 записей в коллекции за один пакет.
- 60 запросов в минуту на адрес для каждого из эндпоинтов.

## Что не сделано

- **Compaction надгробий.** Они копятся вечно. Нужна фоновая чистка записей,
  удалённых больше N дней назад, на сервере и на клиенте.
- **Слияние настроек.** Сейчас документ настроек заменяется целиком по времени.
  Правка разных настроек на двух устройствах приведёт к потере одной из них.
- **Уведомление о конфликте.** LWW работает молча. Для заметок и сумм это
  приемлемо, но пользователь не узнает, что его правка проиграла.
