# Food Scanner

Распознавание еды по фотографии. Главное решение здесь — не «какая модель»,
а **что именно у модели спрашивать**.

## Почему не «фото → калории»

Vision-модель по снимку не видит:

- сколько масла ушло на сковороду;
- сколько сахара в соусе и заправке;
- что внутри сложного блюда;
- сколько порция весит на самом деле.

Ответ «643 ккал» на фотографию она даст — и он будет правдоподобным числом
без опоры на что-либо. Поэтому система разделена на два шага:

```
РАСПОЗНАВАНИЕ                          РАСЧЁТ ЦЕННОСТИ
что видно и сколько примерно  ───→     сколько в этом калорий
(vision-модель)                        (справочник × вес)
```

Модель отвечает за перечень компонентов, вес и уверенность. Калорийность
берётся из справочника: «рис отварной» — это всегда 130 ккал на 100 г,
независимо от того, под каким углом снята тарелка.

## Конвейер

```
ФОТО
 ↓  клиент: MIME, размер, сжатие до 1280 px, снятие EXIF
ЗАГРУЗКА                         src/lib/utils/image.ts
 ↓  сервер: подпись Telegram, ограничение частоты, сигнатура файла
ПРОВЕРКА                         routes/api/nutrition/analyze, server/ai/image.ts
 ↓
AI VISION                        server/ai/providers/anthropic.ts + prompt.ts
 ↓  компоненты: название, вес, способ приготовления, уверенность
ПРОВЕРКА ОТВЕТА                  server/ai/schema.ts  (Zod)
 ↓
РАСЧЁТ ЦЕННОСТИ                  server/ai/nutritionProvider.ts
 ↓  справочник × граммы
УВЕРЕННОСТЬ                      server/ai/pipeline.ts
 ↓
ПОКАЗ ПОЛЬЗОВАТЕЛЮ               components/nutrition/food-scanner.svelte
 ↓  правка названий и граммов
ПОДТВЕРЖДЕНИЕ
 ↓
plannerStore → IndexedDB → очередь синхронизации → сервер
```

**Ни одна ветка не ведёт из распознавания прямо в дневник.** Записи создаёт
только `addScannedFood` в `services/nutritionService.ts`, и вызывается она
из обработчика кнопки «Добавить в дневник».

## Формат результата

```ts
{
  items: [{
    id, name, estimatedGrams,
    calories, protein, fat, carbs,   // для указанного веса
    per100g,                          // основа пересчёта
    nutritionSource: 'database' | 'estimate',
    confidence, notes?
  }],
  totals: { calories, protein, fat, carbs },
  overallConfidence
}
```

`per100g` уезжает на клиент намеренно: когда человек правит граммы, значения
считаются заново от ста граммов, а не пропорцией от прежней порции. Цепочка
«умножили на 1,1, потом ещё на 1,1» копит ошибку округления, и после десятка
нажатий «+» числа перестают сходиться. Формулы общие для сервера и клиента —
`src/lib/utils/foodScan.ts`.

`nutritionSource` различает проверяемое и предположение: `database` — запись
справочника, `estimate` — оценка модели для продукта, которого в справочнике
нет. У таких компонентов уверенность принудительно понижается.

## Справочник питания

`NutritionProvider` — интерфейс из двух методов (`searchFood`, `getNutrition`).
Реализация по умолчанию — локальная таблица примерно на 190 продуктов
(`providers/nutritionData.ts`) со значениями для готового блюда: «рис отварной»,
а не «рис сухой».

Сопоставление идёт по словам, а не по точному равенству строк: модель возвращает
«Куриное филе на гриле», в таблице лежит «Куриная грудка». Слова сравниваются
по общему началу из четырёх букв — это дёшево закрывает падежи («овощи»,
«овощами», «овощная»). Точность в оценке весит больше полноты: одно совпавшее
слово из четырёх — не найденный продукт, и такой запрос уходит в оценку модели.

Способ приготовления участвует в поиске: «курица» и «курица жареная» — это 165
и 230 ккал на сто граммов.

## Уверенность

Показываются три уровня, а не проценты: «уверенность 74,3 %» изображала бы
точность, которой нет — это самооценка модели, а не измеренная величина.

Общая уверенность — минимум из двух величин: оценки модели и средней
по компонентам, взвешенной по граммам. Неуверенно опознанный соус на 20 г
не должен ронять оценку блюда так же, как второе на 300 г.

При низкой уверенности интерфейс говорит прямо: «Проверьте порцию — по фото
её трудно определить».

## Плохие фотографии

Темнота, размытие, отсутствие еды в кадре, пустой ответ модели — для
пользователя это один исход: показывать нечего. Pipeline отвечает
`NO_FOOD_DETECTED`, интерфейс предлагает переснять или ввести вручную.
Выдуманный результат здесь хуже честного отказа: он попадёт в дневник
как настоящий.

## Состояния интерфейса

`idle → preparing → preview → analyzing → result → confirmed`, плюс `error`
и `manual` в любой момент. У каждого состояния свой экран. Во время анализа
показывается не бесконечный спиннер, а что происходит: «Отправляем фото…»,
«Рассматриваем фото и определяем продукты…», «Рассчитываем примерные значения…».

Главная кнопка Telegram дублирует основное действие там, где оно ровно одно:
«Распознать» на предпросмотре и «Добавить в дневник» на результате.

## Порция после скана

Модель оценивает вес по фото, а человек знает свою тарелку лучше. Поэтому
на экране результата есть порция всего блюда: ×0,5, ×0,75, ×1, ×1,25, ×1,5, ×2,
степпером или сразу нужным шагом. Калории и БЖУ пересчитываются на лету,
до сохранения.

Пересчёт идёт от исходного веса каждого компонента (`scalePortion`
в `src/lib/utils/foodScan.ts`): ×2 → ×1 возвращает ровно то, что было,
округления не копятся. Ручная правка граммов у компонента становится
новой основой для множителя.

Если модель нашла несколько компонентов, у каждого есть галочка. Снятая
галочка исключает компонент из итога и из записи. Это обратимо, в отличие
от «Убрать».

## Быстрая запись

Первый экран шторки еды начинается не с камеры, а с того, что человек уже ел.
Считается всё из записанного, новых таблиц на сервере нет.

| Что                           | Откуда                                          |
| ----------------------------- | ----------------------------------------------- |
| «Часто»                       | `frequentFoods` — топ по частоте за 30 дней     |
| «Недавно»                     | `recentFoods` — последние разные блюда          |
| «Избранное»                   | `settings.favoriteFoods`, звёздочка у блюда     |
| «Повторить вчерашний завтрак» | `yesterdayMeals` — приёмы вчера, пустые сегодня |

Касание записывает блюдо сразу, с теми же граммами. Карандаш или долгое
нажатие открывают форму с порцией. После записи внизу на 5 секунд
появляется «Записано · Отменить», и отмена удаляет ровно созданные записи.

Избранное лежит в настройках, потому что они уже синхронизируются. Список
сливается **поштучно** по ключу блюда и времени правки — и на сервере
(`mergePlannerSettings`), и на устройстве (`mergeSettingsFromSync`). Поэтому
звёздочка с телефона не пропадает, когда планшет меняет цель калорий. Снятая
звёздочка хранится отметкой `removedAt`, чтобы снятие доехало до других
устройств. Старые версии приложения поле не знают, но и не стирают:
настройки читаются поверх значений по умолчанию, а сервер добирает список
из сохранённого.

## Приватность

Фотография живёт только в памяти обработчика: на диск не пишется, в базу
не кладётся, после ответа теряется вместе с запросом. Дневнику нужен результат,
а не снимок.

EXIF снимается ещё на клиенте: пересжатие через canvas отбрасывает метаданные
целиком, вместе с координатами съёмки и моделью телефона. Ориентация при этом
восстанавливается заранее (`imageOrientation: 'from-image'`), иначе снимок
уехал бы на сервер повёрнутым.

Данные пользователя Telegram провайдеру ИИ не передаются: уходит только
изображение и промпт.

## Тот же конвейер в чате с ботом

Фото, присланное боту, проходит ровно через `runFoodScan`. Разбор кладётся
в `pending_scans` и показывается сообщением с кнопками «Записать» / «Отмена»:
в переписке нет экрана правки, но правило «сначала человек видит, потом
записывается» действует и там. Запись выдаётся из таблицы ровно один раз,
поэтому повторное нажатие кнопки не задвоит блюдо.
