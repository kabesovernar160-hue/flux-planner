# Бэкенд

## База данных

**Drizzle ORM + SQLite** (`better-sqlite3`).

SQLite выбрана как стартовая точка осознанно: она поднимается из файла без
учётных данных, поэтому синхронизацию можно было написать и **проверить тестами
сразу**, а не после того, как кто-то заведёт Postgres.

**Для продакшена на serverless-хостинге файловая база не годится** — у каждого
инстанса будет свой файл. Переезд на Postgres:

1. `npm i postgres` и заменить импорт в `src/lib/server/db/client.ts`
   на `drizzle-orm/postgres-js`.
2. Поменять `sqliteTable` на `pgTable` в `schema.ts`, `integer(mode:'boolean')` на
   `boolean`, `real` на `numeric` или `doublePrecision`.
3. Заменить `BOOTSTRAP` на миграции `drizzle-kit`.

Схема и репозитории при этом не меняются — на это они и разделены.

## Таблицы

```
users             id, telegram_user_id (UNIQUE), username, first_name, timezone, …
planner_state     user_id (PK), schema_version, settings (JSON), updated_at
food_entries      + date, name, grams, calories, protein, fat, carbs, source
habits            + name, icon, frequency, target_days (JSON), archived
habit_completions + habit_id, date, completed
finance_entries   + date, type, amount, category, note
daily_nutrition   + date, цели и выпитая вода
daily_finance     + date, budget
```

Каждая синхронизируемая таблица несёт `id, user_id, created_at, updated_at, deleted_at`.

`user_id` в каждой строке — это **граница безопасности**, а не денормализация
ради удобства. Любой запрос обязан по нему фильтровать.

## Репозитории

`src/lib/server/db/repositories.ts`

- `UserRepository` — поиск и заведение пользователя по Telegram ID
- `PlannerRepository` — документ настроек
- шесть `SyncRepository` — по одному на синхронизируемую таблицу

Шесть таблиц отличаются только набором полезных полей, а правила выборки
и слияния у них одни, поэтому реализация одна и параметризованная. Шесть почти
одинаковых классов разъехались бы при первой же правке логики конфликтов.

Отдельно `src/lib/server/db/queries.ts` — чтения для отчётов (срез одного дня).
У синхронизации задача «отдать всё изменённое с момента X», у отчёта — «дай день»;
смешивать это в одном интерфейсе значит получить репозиторий, непонятный нигде.

## API

| Метод | Путь                     | Назначение              |
| ----- | ------------------------ | ----------------------- |
| POST  | `/api/auth/telegram`     | Кто я для сервера       |
| POST  | `/api/sync/push`         | Отправить изменения     |
| GET   | `/api/sync/pull`         | Забрать изменения       |
| POST  | `/api/nutrition/analyze` | Распознать еду по фото  |
| POST  | `/api/telegram/webhook`  | Входящие сообщения бота |
| POST  | `/api/telegram/notify`   | Уведомление самому себе |
| POST  | `/api/cron/daily`        | Ежедневная рассылка     |
| POST  | `/api/account/delete`    | Удаление своих данных   |
| GET   | `/api/health`            | Живость для мониторинга |

Все эндпоинты, кроме вебхука и крона, требуют подписи Telegram в заголовке
`X-Telegram-Init-Data`. Это относится и к `/api/nutrition/analyze`: он тратит
деньги на каждом вызове и пишет от имени конкретного пользователя, поэтому
открытым не оставлен. Разбор фотографии описан в
[food-scanner.md](food-scanner.md).

## Формат ошибок

```json
{ "error": { "code": "RATE_LIMITED", "message": "Слишком много запросов" } }
```

| Код | Когда                                            |
| --- | ------------------------------------------------ |
| 400 | Не прошла валидация                              |
| 401 | Подпись не проверена                             |
| 403 | Неверный секрет крона                            |
| 413 | Файл слишком большой                             |
| 429 | Превышена частота                                |
| 500 | Внутренняя ошибка или отсутствующая конфигурация |
| 422 | Еду на фото определить не удалось                |
| 502 | Сбой у провайдера ИИ                             |
| 504 | Провайдер не ответил вовремя                     |

Наружу уходят только код и текст для человека. Стектрейсы, сообщения провайдера
и тем более ключи не покидают сервер: ответ об ошибке — такой же канал утечки,
как и успешный.

## Ограничение частоты

`src/lib/server/rateLimit.ts` — в памяти процесса. **Временная мера.**
Счётчики не переживают перезапуск и не общие для нескольких инстансов,
а ключом служит IP, который в мобильных сетях делят тысячи абонентов.

Настоящий ограничитель должен считать по идентификатору пользователя из
проверенного initData и хранить счётчики во внешнем хранилище (Redis, Upstash).

## База и миграции

Драйвер — libSQL (это SQLite, умеющий работать и как файл, и как удалённая база
по HTTP). Один диалект для разработки и продакшена: схема, запросы и поведение
совпадают, и «у меня работало» перестаёт быть отдельным классом ошибок.

Схема создаётся не на старте одним куском SQL, а пронумерованными миграциями
(`db/migrations.ts`) с отметками в `schema_migrations`. Первый шаг написан через
`IF NOT EXISTS`, чтобы базы, созданные прежним способом, подхватились без потери
данных. Шаги не переставляются и не переписываются после выката.

`getReadyDb()` ждёт применения миграций, `ensureSchema()` делает это один раз
на процесс. Полагаться только на хук старта нельзя: тесты, скрипты и обработчик
вебхука приходят в базу своими путями.

## Ограничение частоты

`server/rateLimit.ts` — счётчики в таблице `rate_limits`, окно фиксированное,
проверка и увеличение делаются одним upsert (иначе два параллельных запроса
прочитали бы одно значение и предел разошёлся бы).

Счётчики в базе, а не в памяти процесса: иначе предел обнуляется при каждом
развёртывании и считается отдельно на каждом инстансе, то есть платный вызов
распознавания можно раскрутить простым чередованием. Недоступная база не запирает
вход — запрос пропускается, а сбой пишется в лог: частичный сбой не должен
становиться полным отказом.

Протухшие окна вычищает ежедневный cron.

## Конфигурация

`server/config.ts` собирает переменные окружения в одном месте и проверяет их
на старте (`hooks.server.ts`). Проблемы делятся на fatal и warning: без токена
бота приложение бесполезно целиком и не поднимается, а без ключа ИИ просто
работает без распознавания по фото.
