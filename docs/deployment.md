# Развёртывание

## Переменные окружения

Скопируйте `.env.example` в `.env`. Файл закрыт в `.gitignore`.

Конфигурация проверяется **при старте сервера**: без обязательных значений
приложение не поднимается и пишет, чего не хватает. Это сделано намеренно —
«поднялось и молча не работает» обходится дороже, чем «не поднялось с понятной
ошибкой».

| Переменная                | Обязательна         | Что ломается без неё                                                    |
| ------------------------- | ------------------- | ----------------------------------------------------------------------- |
| `TELEGRAM_BOT_TOKEN`      | да                  | Нечем проверить подпись → приложение не стартует                        |
| `DATABASE_URL`            | да в продакшене     | Файловая база в проде требует `ALLOW_FILE_DATABASE=true`                |
| `DATABASE_AUTH_TOKEN`     | для удалённой базы  | libSQL-хостинг не пустит без токена                                     |
| `TELEGRAM_MINI_APP_URL`   | для бота            | Бот не покажет кнопку открытия приложения                               |
| `TELEGRAM_WEBHOOK_SECRET` | для бота            | Вебхук отвечает 401 на всё                                              |
| `AI_API_KEY`              | для распознавания   | В разработке работает мок, в продакшене эндпоинт отвечает ошибкой       |
| `CRON_SECRET`             | для рассылки        | Эндпоинт ежедневной рассылки отключён                                   |
| `ORIGIN`                  | да для `node build` | Node-адаптер отвергает POST-запросы без совпадающего Origin             |
| `BODY_SIZE_LIMIT`         | да для фото         | По умолчанию 512 КБ: снимок с телефона не доедет до сканера             |
| `PORT`                    | нет                 | По умолчанию 3000                                                       |
| `DOMAIN`                  | для docker compose  | Compose не соберёт `ORIGIN`, Caddy не поймёт, на какой домен сертификат |
| `ACME_EMAIL`              | для docker compose  | Caddy не запустится: почта для Let's Encrypt обязательна                |

Все переменные читаются **только на сервере** через `$env/dynamic/private`
и собраны в `src/lib/server/config.ts`. В клиентском бандле ни ключей, ни SDK,
ни системного промпта нет — это проверяется при сборке.

## База данных

Драйвер один для всех окружений — libSQL. Локально это файл, на хостинге —
удалённая база по HTTP. Одинаковый диалект означает, что схема и поведение
на ноутбуке и в проде совпадают.

```
# локально
DATABASE_URL=file:flux-planner.db

# продакшен (Turso или свой libsql-сервер)
DATABASE_URL=libsql://имя-организация.turso.io
DATABASE_AUTH_TOKEN=...
```

**Файловая база в продакшене** допустима только на своём сервере с постоянным
диском и подтверждается явно: `ALLOW_FILE_DATABASE=true`. На serverless-хостинге
файл исчезает вместе с контейнером — это потеря данных пользователя, поэтому
без подтверждения приложение не стартует.

### Миграции

`src/lib/server/db/migrations.ts` — пронумерованные шаги, каждый применяется
ровно один раз, отметки лежат в таблице `schema_migrations`. Запускаются
автоматически при старте сервера и в тестах; отдельная команда не нужна.

Правила: шаги не переставлять и не переписывать после выката — на развёрнутой
базе это разъедется с отметками. Изменение схемы — всегда новый шаг в конце.

### Резервные копии

У управляемого libSQL-хостинга копии настраиваются на его стороне (Turso держит
point-in-time restore). Для файловой базы в Docker есть `scripts/backup.sh`:

```bash
./scripts/backup.sh            # копия в ./backups
./scripts/backup.sh /mnt/диск  # или куда удобно
```

Скрипт снимает копию командой sqlite3 `.backup` **внутри работающего
контейнера** и забирает файл на хост. Просто скопировать `flux-planner.db`
нельзя: при включённом WAL часть данных лежит в соседнем файле, и в снимок
попадёт несогласованное состояние. Копии старше двух недель удаляются.

Восстановление описано в шапке скрипта: остановить `app`, положить файл
в том, запустить обратно. Проверьте это хотя бы раз на копии — непроверенная
резервная копия не копия.

## Выкат на свой сервер

Всё, что нужно на сервере, — Docker. Node, nginx и certbot ставить не нужно:
приложение едет в образе, а Caddy перед ним сам получает и продлевает
сертификат Let's Encrypt.

### 1. Сервер и домен

Хватит самого маленького VPS: 1 ГБ памяти, 10 ГБ диска. В DNS — A-запись
с домена на адрес сервера. Снаружи должны быть открыты порты 80 и 443:
80 нужен для выпуска сертификата, закрыв его, вы получите сервер без HTTPS.

Проверить, что домен доехал:

```bash
dig +short ваш-домен
```

### 2. Docker

```bash
curl -fsSL https://get.docker.com | sh
```

### 3. Код

```bash
git clone <адрес репозитория> /opt/flux-planner
cd /opt/flux-planner
```

Репозиторий приватный: в нём нет секретов, но и выкладывать его наружу
незачем. Если удалённого репозитория ещё нет, код можно закинуть через
`rsync -av --exclude node_modules ./ сервер:/opt/flux-planner/`.

### 4. Настройки

```bash
cp .env.example .env
nano .env
```

Заполняются: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `CRON_SECRET`,
`AI_API_KEY`, `DOMAIN`, `ACME_EMAIL`, а также
`TELEGRAM_MINI_APP_URL=https://ваш-домен` и `APP_URL=https://ваш-домен`.

Секреты на сервере должны быть **новые**: те, что лежали на ноутбуке,
светились в туннелях и в истории команд. `DATABASE_URL`,
`ALLOW_FILE_DATABASE`, `ORIGIN` и `BODY_SIZE_LIMIT` задаёт сам compose —
в `.env` их трогать не нужно.

### 5. Запуск

```bash
docker compose up -d --build
```

Первая сборка занимает несколько минут, дальше — меньше минуты. Проверка:

```bash
curl -fsS https://ваш-домен/api/health
docker compose ps
```

`/api/health` отвечает `{"status":"ok"}`, оба контейнера — `running`,
приложение — `healthy`. Если сертификат ещё выписывается, дайте Caddy минуту
и посмотрите `docker compose logs caddy`.

### 6. Бот

Вебхук и профиль бота настраиваются изнутри контейнера — тем же кодом,
что и локально, и без Node на сервере:

```bash
docker compose exec app node scripts/set-webhook.ts
docker compose exec app node scripts/bot-setup.ts
```

После регистрации вебхука **остановите локальный `npm run bot`**: Telegram
доставляет обновления либо в вебхук, либо в поллинг, и запущенный поллинг
будет получать 409 и мешать.

Затем в BotFather: `/mybots` → бот → Bot Settings → Configure Mini App →
прислать `https://ваш-домен`. Там же, если ещё не включено, — Enable Mini App
для кнопки «Открыть» в списке чатов.

### 7. Расписание

Ежедневная рассылка и резервные копии — обычный cron на сервере
(`crontab -e`):

```
0 * * * * curl -fsS -X POST "https://ваш-домен/api/cron/daily?hour=20" -H "Authorization: Bearer СЕКРЕТ" > /dev/null
0 * * * * curl -fsS -X POST "https://ваш-домен/api/cron/daily?kind=habits&hour=12" -H "Authorization: Bearer СЕКРЕТ" > /dev/null
30 4 * * * cd /opt/flux-planner && ./scripts/backup.sh >> backups/backup.log 2>&1
```

Планировщик дёргается **ежечасно**, а `hour` — это местный час получателя:
сообщение получают только те, у кого сейчас это время. Иначе «восемь вечера»
по времени сервера приходило бы кому-то в полдень, а кому-то в три ночи.

`kind=habits` — дневное напоминание о незакрытых привычках, `kind` по
умолчанию — итоги дня. Без `hour` рассылка уходит всем сразу, как раньше.

### Обновление и обслуживание

```bash
git pull && docker compose up -d --build   # выкатить новую версию
docker compose logs -f app                 # логи приложения
docker compose restart app                 # перезапуск
docker compose down                        # остановить всё; данные в томе остаются
```

Данные лежат в томе `flux-data` и переживают пересборку, `down` и обновление
образа. Удаляются они только вместе с томом (`docker compose down -v`) —
этой команды стоит избегать.

### Без Docker

```bash
npm ci
npm run build
ORIGIN=https://ваш-домен node build
```

`node build` — обычный Node-сервер, который живёт за любым обратным прокси
(nginx, Caddy, Traefik). TLS и HTTP/2 — задача прокси.

## Проверка живости

`GET /api/health` отвечает `200 {"status":"ok"}` или `503`, если база недоступна
или конфигурация неполная. Наружу уходит только факт — ни версий, ни адреса базы,
ни значений переменных: эндпоинт открыт всему интернету.

Подходит для балансировщика, Kubernetes-проб и внешнего мониторинга.

## Логи и разбор инцидентов

Каждый запрос получает короткий идентификатор, он же уезжает в заголовке
`X-Request-Id` и в текст ошибки для пользователя. По нему запись находится
в логах: `[http] fa482a0b POST /api/nutrition/analyze 200 812ms`.

В логи намеренно не попадает строка запроса: там бывают пользовательские данные,
а журналы живут дольше и видны шире, чем кажется.

## Заголовки безопасности

Проставляются в продакшене (`src/hooks.server.ts`): CSP, `nosniff`,
`referrer-policy`, `permissions-policy`. В CSP явно разрешены `telegram.org`
для SDK и `frame-ancestors` для веб-клиента Telegram — без этого Mini App
не откроется на десктопе.

В разработке заголовки не ставятся: они отключили бы горячую перезагрузку.

## Бот

Для кнопки «Открыть» в списке чатов включите Main Mini App в BotFather
(Bot Settings → Configure Mini App). Вебхук должен принимать `pre_checkout_query`
— иначе платежи звёздами будут отменяться; скрипты регистрации это уже делают.

```bash
# продакшен: вебхук
APP_URL=https://ваш-домен npm run bot:webhook

# команды, кнопка меню и описания бота
npm run bot:setup

# локально: long polling
npm run bot
```

`bot:setup` берёт адрес из `TELEGRAM_MINI_APP_URL`, поэтому после переезда
на другой домен его нужно выполнить снова — иначе кнопка меню останется
на старом адресе. Имя и аватар меняются только в BotFather.

## Документы

Политика конфиденциальности и условия использования лежат в приложении:
`/privacy` и `/terms`. Контакт поддержки в них один на оба документа —
`SUPPORT_CONTACT` в `src/lib/legal.ts`; перед выкатом там должен стоять
работающий аккаунт. Ссылки на эти же адреса задаются в BotFather
(Bot Settings → Privacy Policy) — Telegram показывает их в меню бота.

## Ежедневная рассылка

`POST /api/cron/daily` с заголовком `Authorization: Bearer <CRON_SECRET>`.
Вызывается внешним планировщиком (cron на сервере, Vercel Cron, Cloudflare
Workers — любым, кто умеет дёрнуть URL по расписанию). Заодно вычищает
протухшие счётчики ограничителя частоты.

```bash
0 * * * * curl -fsS -X POST "https://ваш-домен/api/cron/daily?hour=20" \
  -H "Authorization: Bearer $CRON_SECRET" > /dev/null
```

Параметры: `hour` — **местный час получателя**, планировщик при этом
вызывается ежечасно и пишет только тем, у кого сейчас это время;
`kind=habits` — напоминание о незакрытых привычках вместо итогов дня.
Без `hour` сообщение уходит всем сразу, независимо от их часового пояса —
так работали прежние расписания.

## Масштабирование

Приложение не хранит состояние в памяти процесса: сессий нет (подпись
проверяется на каждом запросе), счётчики частоты лежат в базе. Поэтому
инстансов может быть несколько за одним балансировщиком — специальной
настройки для этого не требуется.

Узкое место при росте — база. Порядок действий: сначала управляемый libSQL
с репликами для чтения, дальше — переезд на Postgres (меняется диалект Drizzle
и драйвер, схема и репозитории остаются).
